# xacpx 升级 acpx 0.13.1 → 0.15.1：影响评估与实施方案

> 日期：2026-09-08  
> 目标仓库：`gadzan/xacpx`  
> 当前 xacpx：`0.24.3-beta.0`（main）  
> 当前依赖：`acpx: 0.13.1`  
> 目标依赖：`acpx: 0.15.1`（建议继续 exact pin）

---

## 0. 结论先行

**建议升级到 acpx 0.15.1，而且值得尽快做。**

这次升级不只是常规 bugfix。0.15.x 新增了两个对 xacpx Runtime Engine 非常契合的正式 embedding API：

1. `AcpRuntimeOptions.processLifecycle`：在 ACP agent 启动前、启动后、启动失败和退出时提供关联的生命周期事件，其中 `onBeforeSpawn` / `onSpawned` 是 **awaited admission boundary**；
2. `AcpRuntimeOptions.agentProcessEnv`：给 Runtime 所拥有的 agent child 提供**不持久化、构造期快照、重连继续生效**的 child-only 环境覆盖。

此外 0.13.2～0.15.1 还带来：

- Runtime `promptStarted` 从“已经拿到 prompt Promise”强化为“**底层可写 ACP transport 已接受精确 prompt 请求**”；
- `setConfigOption()` 返回 agent 接受后的 `configOptions` 快照，且 acpx 修复了 reconnect 后 model/config selection 恢复；
- turn result 可保留 opaque `_meta`；
- Windows terminal cleanup 更可靠，hung `taskkill` 会超时并保留可重试状态；
- agent spawn `ENOENT` 提供稳定的 `AGENT_SPAWN_ENOENT` detail；
- 新增 MiniMax Code (`mcode acp`) built-in；
- 0.15.1 默认对 **agent → acpx 的 incoming ACP message** 施加 64 MiB raw-byte 上限，并提供 `ACPX_MAX_ACP_MESSAGE_BYTES` override；
- 新增 `ACPX_TERMINAL_MAX_OUTPUT_BYTES` host ceiling。

### 最重要的架构判断

升级后**不要**把 xacpx 当前的 Runtime Worker ownership / fence / orphan recovery 整套删掉。

acpx 官方文档明确说明，`processLifecycle`：

- 不负责持久化 process lease；
- 不负责 embedding host 重启后的 reconcile；
- 不负责 arbitrary descendants；
- 不保证 abrupt owner death 后的 cleanup。

而且 acpx 0.15.1 的 `TerminalManager` 仍直接从 embedding client 进程 spawn terminal command；这些 terminal 子进程不是 `processLifecycle` 所报告的 ACP agent root。因此它不能解决 xacpx 之前 PR #312 审查里识别出的“dead Windows root + PID reuse + root-independent ownership proof”信息缺失问题。

**正确方向是：**

> 用 acpx 0.15.1 的正式 hooks 替换 xacpx 对“直接 ACP agent 启动”的推断和临时 env 方案；保留 xacpx 的 Host/Worker crash-safety 外壳。把 upstream 已经拥有的语义交还 upstream，把 xacpx 只需要承担的跨 Host 生命周期/策略留在 xacpx。

建议分成两轮：

- **PR A — 纯升级/兼容性基线**：0.13.1 → 0.15.1，先不做 ownership 架构改造，把所有 pinned tests 和行为差异重基线；
- **PR B — 利用 0.15 公共契约做简化**：引入 `agentProcessEnv`、`processLifecycle`、accepted config response、`_meta`、host limits；在新测试成立后，再删除被正式 API 替代的局部 workaround。

## 1. 当前 xacpx 与 acpx 的耦合面

### 1.1 依赖与运行时边界

xacpx 当前 `package.json` 精确依赖 `acpx: 0.13.1`，并将 acpx 作为 build external。Node engine 是 `>=22.13.0`；acpx 0.15.1 也是 `>=22.13.0`，所以没有 Node 版本门槛变化。

Runtime Engine 已经做了正确的边界收口：

- `src/bridge/engine/runtime/runtime-adapter.ts` 是主 `acpx/runtime` public boundary；
- 上层只依赖 `runtime-contract.ts` 的 xacpx-owned narrow types；
- 另有一个历史例外：`src/transport/agent-registry.ts` lazily require `acpx/runtime`。

这意味着 0.15.1 的大多数 API 变化可以继续吸收在 adapter 层，不应该向 bridge/channel 层扩散 acpx 类型。

### 1.2 Runtime Worker ownership 是 xacpx 自己的安全边界

当前 Runtime Engine 是“一 session → 一 Runtime Worker process → 一 `AcpRuntime` + persistent handle”。Worker 本身是 xacpx 的 lifecycle primitive。

xacpx 当前已经实现了：

- generation-bound worker fence；
- `claiming / owned / admitted / discharging / discharged / spooled / deleting` 状态机；
- Host restart 前的 discharge/refuse；
- Windows handle-stable identity / CIM descendant convergence；
- residual orphan registry；
- shutdown control request 不计入 business gate，并且 **drain 后才 ACK**；
- dead Windows root 没有 root-independent proof 时 fail closed，不再用 historical `ParentProcessId` 猜 ownership。

这些是 Host/Worker crash-safety，不是 acpx 0.15.1 process hooks 的替代目标。

### 1.3 当前 Runtime Engine 的几个“0.13.1 时代形状”

当前代码中有几处明显绑定 0.13.1：

- `runtime-adapter.ts` 没有 `agentProcessEnv` / `processLifecycle`；
- `XacpxTurnResult` 没有 `_meta`；
- `setConfigOption()` 在 adapter 层固定返回 `Promise<void>`，丢弃 upstream accepted snapshot；
- `RuntimeWorkerEnsureParams` 没有 runtime child env；
- `runtime-worker-main.ts` 对 effort 要先 `getStatus()` 找真实 config id，再 `setConfigOption()`；
- capability、compat、permission differential、record compatibility 等大量测试 fixture 直接写着 `0.13.1`；
- 部分 permission differential 甚至冻结了 0.13.1 bundle 内部 helper 的语义。

升级不能只改 `package.json` 和 lockfile。

## 2. acpx 0.13.1 → 0.15.1 版本差异

## 2.1 0.13.2：session controls / reconnect correctness

对 xacpx 最相关的修复：

- reconnect 后恢复已保存的 model / config selections；
- accepted model change 后 reasoning effort 保持一致；
- embedding client 可以拿到 agent 接受后的 configuration，而不会把未选择的 defaults 错当成用户偏好持久化。

### 对 xacpx 的意义

xacpx 当前同时保存自己的 model/effort 偏好，又让 acpx persistent record 保存状态。0.13.2 之后，acpx 的 record 更可信，重复的“恢复/推断”逻辑可以逐步减少。

但**不建议第一轮就删除 xacpx 自己的 preference state**：xacpx 仍需要跨 reset、record 缺失、用户配置层的稳定偏好。先用 differential tests 证明同一语义，再决定哪个层是 source of truth。

---

## 2.2 0.14.0：promptStarted 语义强化

0.13.1：`promptStarted` 的语义接近“`connection.prompt()` 已返回 request Promise”。

0.14+：只有在**精确 prompt request 已被 writable ACP transport 接受**后才 resolve；如果 write 失败则 reject。

### 对 xacpx 的意义

当前 `runtime-worker-main.ts` 已经：

1. 先把 `activeTurn` 发布；
2. `await turn.promptStarted`；
3. 再消费 event stream。

升级后这段代码语义更强，不需要 xacpx 自己再定义“prompt 到底算没算发出去”的第二套启动态。

**可以更优雅地处理：**

- 把 `promptStarted` 作为唯一的“已提交到 ACP transport”里程碑；
- prompt write 失败时直接按 turn/start failure 路径处理，不做“已启动但空结果”的兼容猜测；
- benchmark / rename / cancellation race tests 可以用这个 stronger barrier，减少人为 deferred seam。

这里主要是**语义简化与测试收紧**，不是大规模删代码。

---

## 2.3 0.14.0：Windows terminal cleanup 与 spawn ENOENT

新增/修复：

- hung Windows `taskkill` 有超时；
- cleanup 不完整时不再报告成功，并保留 terminal state 供 retry；
- terminal stdout/stderr stream error 不再带崩 host；
- agent spawn `ENOENT` 提供 `AGENT_SPAWN_ENOENT` detail 和更明确 remediation。

### 对 xacpx 的意义

**收益：**

- 正常 ACP terminal release 的成功率更高；
- worker EOF 时需要 xacpx residual spool 的概率应下降；
- Windows 卡死 cleanup 不会无限阻塞 acpx release；
- agent 未安装 / PATH 失效可用稳定 detail 区分，而不是只靠 message regex。

**不能因此删除：**

- `terminateWindowsDescendantsOf()`；
- worker EOF convergence；
- residual registry；
- fence discharge。

原因：这些处理的是 **embedding Host/Worker 异常死亡** 和 acpx client 自己来不及正常 release 的场景，层级不同。

---

## 2.4 0.15.0：`agentProcessEnv`

新接口：

```ts
createAcpRuntime({
  ...,
  agentProcessEnv: {
    KEY: "value",
  },
})
```

关键语义：

- 在 `createAcpRuntime()` 时 snapshot；
- 只作用于 acpx 所拥有的 agent child；
- probes / new sessions / controls / reconnects 都一致使用；
- 不修改 parent `process.env`；
- 不写入 session record / event / status / diagnostics；
- precedence：protected auth > `agentProcessEnv` > persisted `sessionOptions.env` > inherited parent env；
- Windows env key collision 使用 case-insensitive 规则。

### 这是 xacpx 最直接可用的改进之一

当前 CLI transport 已经可以把 per-agent `env` 传给 queue owner/adapter；Runtime Worker protocol 却没有 env 字段。历史设计文档还明确禁止把 `{...process.env}` 塞进 `sessionOptions.env`，因为那会把 host 临时环境持久化进 acpx session。

0.15.0 后可以把 Runtime Engine 的 env parity 做干净：

```text
xacpx resolved agent env
        |
        v
RuntimeWorkerEnsureParams.agentProcessEnv
        |
        v
ensureIdentityKey includes normalized env snapshot
        |
        v
createXacpxRuntimeAdapter({ agentProcessEnv })
        |
        v
createAcpRuntime({ agentProcessEnv })
        |
        v
probe / first launch / reconnect 都一致
```

### 推荐改动

#### `runtime-worker-protocol.ts`

新增：

```ts
agentProcessEnv?: Record<string, string>;
```

#### `runtime-worker-main.ts`

`ensureIdentityKey()` **必须包含** env snapshot。

原因：upstream 在 Runtime 构造时 snapshot；同一个 worker 内改变 env 不会更新已有 runtime。若 A env → B env 仍 warm reuse worker，会静默继续用旧 env。

因此规则应该是：

> env 是 Runtime construction identity，不是 mutable session option。env 改变必须 recycle worker。

#### `runtime-adapter.ts`

`CreateXacpxRuntimeAdapterOptions` 加 `agentProcessEnv`，原样传给 `createAcpRuntime()`。

### 能删除/避免的东西

- 不再需要为了 Runtime Engine 把 transient agent env 复制进 persisted `sessionOptions.env`；
- 不需要修改 Runtime Worker 的全局 `process.env` 来“间接”让 agent 继承；
- 不需要在 reconnect 时由 xacpx 手工再注入一次 env；upstream runtime 自己保证一致。

### 不能替代 `acpx-agent-overlay.ts`

`agentProcessEnv` 是 env，不是 argv registry。

当前 `xacpx-managed-*` overlay 解决的是 CLI/queue-owner 路径的 **structured argv alias / command identity**，不能因为有 `agentProcessEnv` 就删。

## 2.5 0.15.0：`processLifecycle`

新接口：

```ts
processLifecycle: {
  onBeforeSpawn(launch) {},
  onSpawned(process) {},
  onSpawnFailed(failure) {},
  onExit(exit) {},
}
```

事件带：

- unique `launchId`；
- `scope`：`client` / `runtime-session(sessionKey)` / `runtime-probe(agent)`；
- immutable `command` / `args` / `cwd`；
- spawned/exit 带 child `pid` + timestamp；
- env value 不进入生命周期事件。

其中：

- `onBeforeSpawn` await；reject → 不 spawn；
- `onSpawned` await；reject → upstream 会终止刚 spawn 的 child，然后让 startup 返回错误；
- `onSpawnFailed` / `onExit` best-effort、不 await。

### 对 xacpx 的最大价值：把“agent launch admission”放到真实 spawn 边界

现在 xacpx 的 worker fence 主要知道 Runtime Worker 自己的 PID、phase 和 generation；agent descendant 的存在是通过业务 RPC admission + 后续 process-tree convergence 间接覆盖。

0.15.1 可以新增一个**轻量的 direct-agent lease/evidence layer**：

```text
worker generation G
  |
  | onBeforeSpawn(launchId L, runtime-session S)
  v
持久化 pending agent launch evidence (G,L,S,argv hash)
  |
  | onSpawned(pid P, startedAt T)  [awaited]
  v
原子升级为 live agent evidence (G,L,P,T)
  |
  | onExit(...)
  v
best-effort 标记 exited / retire
```

如果 `onBeforeSpawn` / `onSpawned` 的 durable write 失败：**拒绝 admission**。尤其 `onSpawned` 失败时，acpx 自己负责把刚拉起的 agent kill 掉，这比“spawn 成功后由 xacpx 在外面补一条 ownership 记录，补写失败再猜该怎么收拾”更可靠。

### 推荐做法：把它作为 fence 的辅助证据，不要直接扩张主 fence phase

不建议立刻把主 fence 改成十几个 `agent-spawning/agent-live/...` phase。更简单的是：

- 主 `RuntimeWorkerFence` 继续只描述 worker/Host ownership transaction；
- 新增 `RuntimeAgentLeaseStore`（或 fence 内 optional `agentLaunch` 子记录）；
- key 包含 `physicalFenceKey + workerGeneration + launchId`；
- 只在同一 generation 内写；
- `onBeforeSpawn` / `onSpawned` 写入必须有 bounded timeout；
- `onExit` 只是 best effort，不能作为唯一清理证明。

### 它能简化什么

- direct ACP agent PID 不再需要从 session record/process snapshot 推断；
- agent spawn admission 和 ownership evidence 可变成一个真正的事务边界；
- probe 与 session launch 可以通过 `scope` 明确区分；
- crash diagnostics 能明确回答“这个 worker 是否真的 spawn 过 agent、spawn 到哪个 PID、何时开始”。

### 它**不能**简化什么

**不能删除 `RuntimeWorkerFence` / `worker-eof.ts` / Windows residual orphan registry。**

理由有两层：

1. upstream 文档明确说 lifecycle hooks 不做 lease persistence / host restart reconcile / arbitrary descendant cleanup；
2. acpx `TerminalManager` 自己直接 spawn terminal command，process lifecycle hook 出现在 ACP agent `AcpClient` spawn 路径，并不覆盖这些 terminal child。

因此 PR #312 旧审查里那个信息论结论仍成立：

> 如果 Windows worker root 已经死掉，而某个 descendant 没有 root-independent、generation-bound ownership proof，不能只靠历史 ParentProcessId + PID 去自动 kill。

当前 main 已经正确选择 fail closed；0.15.1 不改变这个边界。

## 2.6 0.15.0：turn result `_meta`

0.15.1 `AcpRuntimeTurnResult` 对 completed/cancelled 增加：

```ts
_meta?: Record<string, unknown> | null
```

当前 xacpx `runtime-adapter.mapResult()` 明确只保留：

- status；
- stopReason；
- error。

所以升级后 `_meta` 会被**静默丢掉**。

### 推荐

在 xacpx narrow contract 中加：

```ts
type XacpxTurnResult =
  | { status: "completed"; stopReason?: string; meta?: Record<string, unknown> | null }
  | { status: "cancelled"; stopReason?: string; meta?: Record<string, unknown> | null }
  | ...;
```

adapter 把 upstream `_meta` 映射成内部 `meta`，不把 `_meta` 命名扩散到业务层。

### 使用原则

- producer-supplied opaque metadata；
- 可以用于观测、debug、未来 agent 特性；
- **绝不能用作 auth / authorization / ownership proof**。

这个原则和现在 `text_delta.meta` 的注释保持一致。

## 2.7 0.13.2+：`setConfigOption()` accepted snapshot

0.15.1 Runtime contract 中：

```ts
setConfigOption(...): Promise<SetSessionConfigOptionResponse | void>
```

acpx 自己会根据 response 中的 `configOptions`：

- 更新 current model；
- reconcile sibling config options；
- 只保留用户真正选择过的 desired options；
- 不把 agent 默认值误写成用户 preference。

当前 xacpx adapter 把返回值完全丢弃。

### 推荐

把 xacpx internal API 改成：

```ts
setConfigOption(...): Promise<XacpxConfigOptionSnapshot | undefined>
```

`XacpxConfigOptionSnapshot` 只保留 xacpx 需要的稳定字段，比如：

```ts
{
  options: Array<{
    id: string;
    currentValue?: string;
    // 只增加 UI/状态真正需要的字段
  }>;
}
```

Worker protocol 的 `setConfigOption` response 也返回该 snapshot。

### 能更优雅地处理的点

- `/model`、reasoning effort 改动后，直接用 accepted snapshot 更新展示状态；
- 如果一个 option 的变化连带改变 sibling option，不再假定“我 set 什么，当前就一定是什么”；
- 减少为了确认 config change 再做一遍 `getStatus()` 的需要；
- reconnect 后优先相信 acpx record 的 accepted current state。

### 暂时不要删的点

`applySessionEffort()` 当前为了把 xacpx 的逻辑名 `effort` 映射到 agent 实际 advertised config id，仍需要一次 advertised config discovery。0.15.1 没有提供通用 `setEffort()` API，因此不能简单删掉这段映射。

后续可以缓存 config snapshot，避免每次 effort change 都重新 `getStatus()`。

## 2.8 0.15.1：64 MiB incoming ACP message limit

这是这次升级唯一明确的**默认行为 compatibility change**。

0.15.1 开始：

- agent → acpx 的单个 incoming ACP raw message 默认最大 64 MiB；
- `ACPX_MAX_ACP_MESSAGE_BYTES=<bytes>` 可提高；
- `0` 可禁用；
- warm owner 保留启动时读取到的设置。

### xacpx 风险判断

通常低风险：普通 text/tool/status update 距离 64 MiB 很远。

但以下情况要专门测：

- agent 返回异常巨大的 tool result / diff / structured metadata；
- 某些 adapter 把大文件内容内嵌进单个 session update；
- reconnect 后一次性 replay 巨大消息。

注意：这是 **incoming to acpx** 的限制，不是 xacpx 用户 prompt attachment 的简单“64 MiB 上传限制”。不要把两者混为一谈。

### 推荐策略

- **不要默认设 `0`** 取消上限；
- 第一轮保持 upstream 64 MiB default；
- 增加一条清晰错误映射/日志：出现 overflow 时提示 `ACPX_MAX_ACP_MESSAGE_BYTES`；
- 如确有用户场景，再把它做成 xacpx advanced transport config；
- config 变更要提示 recycle Runtime Worker / warm queue owner 才生效。

---

## 2.9 0.15.1：`ACPX_TERMINAL_MAX_OUTPUT_BYTES`

这个变量给 embedding host 一个**硬 ceiling**，限制 acpx TerminalManager 保存的 stdout+stderr bytes。

语义：

- upstream 默认不设置 host ceiling；
- agent 没有特别请求时，原 64 KiB terminal output default 仍保持；
- agent 请求更大 output buffer 时，host ceiling 可封顶；
- `0` 表示只取消 host ceiling，不代表取消 agent/requested limit；
- 截断保留最新 UTF-8 suffix。

### 推荐 xacpx 处理

建立统一 `AcpxHostPolicy`，供 **CLI queue owner 路径** 和 **Runtime Worker 路径** 一起使用：

```ts
interface AcpxHostPolicy {
  maxIncomingAcpMessageBytes?: number; // undefined = upstream default 64MiB
  terminalMaxOutputBytes?: number;     // undefined = upstream behavior
}
```

落到 child env：

- `ACPX_MAX_ACP_MESSAGE_BYTES`
- `ACPX_TERMINAL_MAX_OUTPUT_BYTES`

第一版建议配置项保持 optional，不擅自改变 upstream default。

**不要通过 `agentProcessEnv` 设置这两个值。**

它们是 acpx embedding client / TerminalManager 自己读取的 host policy，应设置在 Runtime Worker / queue-owner **宿主进程环境**，而不是只传给 agent child。

---

## 2.10 0.15.0：MiniMax Code built-in

acpx 新增 `mcode acp` built-in。

xacpx 当前 `agent-catalog.ts` 虽然从 acpx registry 推导默认 argv/installed hint，但**可展示的 driver 集合仍来自手写 `listAgentTemplates()`**。

当前 `agent-templates.ts` 没有 `mcode` / MiniMax。

因此如果希望升级后用户能在 xacpx UI/CLI 直接选择 MiniMax Code，还需要：

```ts
mcode: { driver: "mcode" }
```

并补 catalog drift test。

这也是一个架构提示：长期可以考虑让“acpx built-in driver 列表”由 registry list API 驱动，而不是 template key 手工枚举；但只有在 acpx public registry 提供稳定 list contract 时再做，不要反射 private internals。

## 3. 哪些 xacpx 代码升级后可以更优雅

| 区域 | 当前方式 | 0.15.1 后建议 | 可删/可减 | 风险 |
|---|---|---|---|---|
| Runtime agent env | Runtime path 没有正式 child-env seam；CLI path另传 env | `agentProcessEnv` | 避免 sessionOptions.env / parent env workaround | env 必须进入 worker identity |
| direct agent launch ownership | worker phase + tree observation间接覆盖 | `processLifecycle` awaited admission + direct-agent lease | 减少 agent PID 推断 | **不能替代 descendant recovery** |
| prompt start | 0.13.1 较弱 barrier | 直接信任 `promptStarted` transport acceptance | 减少二义性/测试 seam | 需要覆盖 write reject |
| model/config | set 后丢 response，状态多靠 status | 透传 accepted `configOptions` | 可减少 status re-query | agent 可连带改 sibling option |
| reconnect config | xacpx + acpx 双层恢复 | 以 acpx accepted record 为 runtime truth，xacpx保留用户 preference | 可减少重复 replay | 先 differential 再删 |
| turn metadata | `_meta` 被丢弃 | narrow `meta` pass-through | 无 workaround，新增能力 | 不可用于安全决策 |
| Windows normal terminal cleanup | upstream 0.13.1 较弱 | 依赖 0.14+ timeout/retry semantics | 降低 xacpx fallback触发率 | crash path仍需自己兜底 |
| agent missing | message/error regex | 识别 `AGENT_SPAWN_ENOENT` detail | 减少字符串匹配 | 保留 broad fallback |
| message size | unlimited incoming | 默认 64MiB +明确 override | 获得安全边界 | 巨大 agent message 兼容风险 |
| terminal output | agent可请求很大保留 | host ceiling | 内存风险更可控 | 不要误设成过小默认 |
| built-ins | template 手工列举 | 加 `mcode` | - | 低 |

## 4. 明确“不应该因为升级而删除”的代码

### 4.1 `RuntimeWorkerFence`

必须保留。

它解决的是：

- Host restart；
- cross-host/same-host double owner；
- destructive delete serialization；
- generation CAS；
- quiescence handoff。

acpx lifecycle hook 不负责这些。

### 4.2 `worker-eof.ts` + Windows orphan residual registry

必须保留。

Terminal command 仍可能是 worker 的直接 child/sibling tree，生命周期 hook 不覆盖。

### 4.3 dead-root Windows fail-closed

必须保留。

除非未来得到真正 root-independent proof，例如：

- Windows Job Object；
- acpx 为**所有** child/terminal descendants 暴露 generation token + stable identity；
- descendant 自带可查询 ownership token。

否则 historical ParentProcessId 仍不够安全。

### 4.4 `acpx-agent-overlay.ts`

不能因为 `agentProcessEnv` 删除。

overlay 是 structured argv / CLI identity 问题，env API 不解决 argv。

### 4.5 xacpx 的 permission policy resolver

0.15.1 release notes 没有声明 permission policy contract 重构。xacpx 有自己的 live policy generation、interactive dispatch、host timeout，仍是产品策略层。

但 pinned private-helper differential test 应重基线，见 §7。

## 5. 推荐最终架构

```text
                        xacpx Host
                           |
                  RuntimeWorkerManager
                           |
               durable RuntimeWorkerFence
                           |
                     Runtime Worker G
          +----------------+----------------+
          |                                 |
   AcpxHostPolicy                     createAcpRuntime
   (worker process env)                     |
   - 64MiB override?                        +-- agentProcessEnv snapshot
   - terminal output cap?                   |
                                             +-- processLifecycle
                                                  |
                                       awaited direct-agent lease
                                     beforeSpawn -> spawned -> exit
                                                  |
                                             ACP agent root

Runtime Worker abnormal EOF
          |
          +-- gate.close + discharging
          +-- Windows descendant convergence (still required)
          +-- residual spool if needed
          +-- discharged/spooled terminal proof
```

核心分层：

- **acpx 负责：** ACP agent 的具体 spawn、agent env、normal terminal lifecycle、Runtime session/config semantics；
- **xacpx Runtime Worker 负责：** 产品 policy、session isolation、permission bridge、MCP bridge；
- **xacpx Host/fence 负责：** crash-safe ownership、cross-process serialization、Host restart、Windows residual recovery。

## B2. direct-agent lifecycle lease

新增建议文件：

```text
src/bridge/engine/runtime/runtime-agent-lease.ts
```

或作为 `RuntimeWorkerFence` 的独立 sidecar store，避免扩大主 phase machine。

### 数据模型

```ts
interface RuntimeAgentLeaseRecord {
  kind: "runtime-agent-launch";
  physicalFenceKey: string;
  workerGeneration: string;
  launchId: string;
  scope: "runtime-session" | "runtime-probe";
  sessionKey?: string;
  agent?: string;
  argvHash: string;
  cwdHash?: string;        // 可选；不直接记录敏感路径时使用 hash
  phase: "pending" | "running" | "exited" | "spawn-failed";
  pid?: number;
  startedAt?: string;
  exitedAt?: string;
}
```

不要持久化完整 env。

### hooks

- `onBeforeSpawn`: bounded durable write pending；失败 reject；
- `onSpawned`: CAS pending → running，写 PID/time；失败 reject，交给 acpx kill child；
- `onSpawnFailed`: best-effort terminal mark；
- `onExit`: best-effort terminal mark。

### timeout

upstream 明确说 admission callback 如果不 settle，会让 startup 无限挂。

所以 xacpx 必须自己包：

```text
withTimeout(durableWrite, e.g. 1~2s)
```

超时视为 admission failure，而不是“继续跑但没记录”。

### B2 测试

- beforeSpawn durable write reject → agent 根本不启动；
- onSpawned write reject → 已启动 child 被 upstream 终止；
- exit 在 onSpawned admission 期间发生 → 最终记录不能被 late running write 覆盖；
- probe scope 不误归 session；
- stale generation 不能写 successor lease；
- callback timeout fail closed；
- onExit 写失败不改变真实 turn/exit outcome。

### B2 边界断言测试（最重要）

必须保留一条测试明确证明：

> 一个由 `TerminalManager` 直接 spawn 的 terminal child **不依赖 processLifecycle lease 作为唯一 ownership evidence**。

防止后续维护者看到新 hook 后误删 worker descendant recovery。

## 9. 不建议做的方案

### 9.1 一次 PR 同时升级 + 删除 fence

不做。风险面完全不同，回归定位困难，而且 lifecycle hooks 的能力也不支持这个结论。

### 9.2 把 `processLifecycle` 当 Windows Job Object

不做。它只是 spawn admission / observation API，不是 OS-level descendant containment。

### 9.3 用 `agentProcessEnv` 传播 ownership token 后假定所有 tool children 都继承

不做。TerminalManager 运行在 embedding client 进程，terminal child 的 env 来源是 terminal request + host process environment；它不天然继承 agent child-only overlay。

### 9.4 为了兼容直接设置 `ACPX_MAX_ACP_MESSAGE_BYTES=0`

不做。64 MiB 是 upstream 新的安全边界，应该先找出真实超限场景，而不是全局取消。

### 9.5 继续复制 acpx private bundle helper

尽量不做。0.15 已经证明 public Runtime contract 在快速增强，xacpx 应继续强化 adapter boundary 和 black-box differential，而不是扩大 private implementation coupling。

## 12. 验收标准

升级完成应满足：

### Compatibility

- 现有 0.13.1 persistent records 在 0.15.1 可 load/reconnect；
- CLI Engine / Runtime Engine 核心语义不倒退；
- permissions parity 不倒退；
- Windows structured argv / managed aliases 不倒退；
- tool-call snapshot normalization 不倒退。

### New contracts

- Runtime agent env 不持久化但 cold/reconnect 一致；
- env change 强制新 worker/runtime；
- beforeSpawn/spawned durable admission 失败均 fail closed；
- `_meta` 不再丢；
- config set 返回 agent accepted snapshot；
- promptStarted 失败准确映射为 prompt write failure。

### Safety

- 64 MiB overflow 有明确、可操作错误；
- 不默认关闭 upstream size limit；
- terminal output host ceiling可配置并在两种 engine path 一致；
- processLifecycle 接入后 Windows dead-root policy 仍 fail closed；
- 任何新 lifecycle store 都 generation-bound；
- durable admission callback 有 timeout；
- secrets/env values 不写 lifecycle records/logs。

## 13. 最终判断

从 xacpx 当前代码结构看，0.15.1 是一个**高价值、低 API 破坏但有一处明确行为兼容风险**的升级：

- API 层大部分是 additive；
- Node baseline 完全兼容；
- Runtime Engine 正好可以利用新 embedding hooks；
- 0.14/0.15 的 session/config/terminal 修复能减少 xacpx 自己兜底的复杂性；
- 0.15.1 的 64 MiB incoming limit 必须认真做 compatibility gate。

真正值得“更优雅”处理的优先级，我建议是：

1. **`agentProcessEnv`：立即采用。** 这是最清晰、收益最大、边界最明确的去 workaround 点；
2. **accepted config snapshot：立即透传。** 减少 model/effort 状态重复推断；
3. **`promptStarted` stronger semantics：收紧测试和状态语义。**
4. **`processLifecycle`：采用，但只做 direct-agent admission/lease，不替换 crash-safety fence。**
5. **`_meta`：低成本 lossless pass-through。**
6. **host limits：统一 CLI/Runtime 配置入口。**
7. **MiniMax Code：补 template。**

如果只做“package.json 0.13.1 改 0.15.1”，会错过这次升级最有价值的部分；如果反过来因为看到了 `processLifecycle` 就删掉 xacpx 的 worker ownership/fence，又会越过 upstream 明确声明的能力边界。

最合适的方案是：**先升级、再沿 public contract 收缩局部 workaround，而不是一次性推翻现在已经加固过的生命周期体系。**
