Bot 群聊：谁先说，谁接着说，谁最后收口

把 DS-Bot、Grok Bot 0.18 和 xacpx 放在同一张桌子上，看三个问题： 一条消息之后谁回答、Bot 之间怎么派活、用户在群里到底看到什么。 结论不是“抄哪个”，而是“xacpx 该补哪一层”。

00 · the short version

三个系统，三种群聊

一句话：xacpx 缺的不是“群”，而是“聊天室感”。它已经是可审计的任务执行型群聊；DS-Bot 和 Grok Bot 值得借的是 依次发言、跳过、过程可见，不是把它们的调度器搬进来。
DS
DS-Bot房间日志 + 发言位

一个房间，一条日志。群自己有一个不跑模型的 Session，用合成的 group_relay 驱动一轮。

  • 普通消息默认先给 admin；everyone 模式按顺序全员。
  • @Name 一发出来就并行开工。
  • 干活 15 秒就让出本轮；结果晚到也发回群。
  • Bot 之间是一棵 work tree，结果自动向上收。
G
Grok Bot 0.18有界轮询

群是一个没有模型的 agent 文件夹。GroupChatOrchestrator 逐成员跑回合。

  • 最多 3 轮 / 10 条；每人每轮最多 2 条。
  • 每轮从“上次用户发言以来”的 @ 重算响应者。
  • (pass) 可以不说；失败也算 pass。
  • 成员复用自己 Session，群历史带 [Group chat] 标签。
xa
xacpxRun + MemberTurn

一次用户请求 = 一个 Run。选中的每个 Bot 一个 MemberTurn，派活用结构化 group_send。

  • Topic 内一次只有一个活动 Run；队列 64。
  • 并行 cohort 受 writer slot / worktree 约束。
  • 结果精确 join，trace 持久化，可恢复。
  • 没有内建轮询、pass、过程发言。

调度

DS-Bot：讨论串行、派活并行；Grok：严格串行；xacpx：同一批并行，没“依次发言”。

协作

DS-Bot：树 + 自动向上收；Grok：异步消息；xacpx：结构化 assignment + work graph。

交互

DS-Bot：过程进群；Grok：流式预览；xacpx：最终结果进群，过程在 trace。

协作：派活、回收、防绕圈

DS-Bot · work tree

A 派给 B 的活是一棵树：B 再派给 C/D 的活挂在下面；B 的回答要等 C/D 都交回，再连同它们的结果一起交给 A。

↓ message_bot
B做 work1
↓ ↓
Cwork2 · parent=work1
Dwork3 · parent=work1
↓ 结果自动向上收
A拿到 B 的回复 + C/D 结果

发给“正在等这件活结果的上游”会被拒绝；结果本来就会自己上去。

Grok · 异步消息

SendToAgent 是发短信，不是 RPC：发完就结束本回合，对方以后自己回；群目标会变成往群里发帖。

没有树、预算或自动回收；靠 prompt 规则“不要 ping-pong 确认”。

05 · target architecture

一个 Run，一条时间线

完整技术方案 ↗
决策：保留“一次用户请求 = 一个 Run”。不建 Room 表、不建 Round 表、不建第二套 scheduler。 Run 增加 shape：single（Direct）、fanout（Lead 派活）、roundtable（依次讨论）。 圆桌在 accept 时预生成所有 MemberTurn，顺序由持久行和 claim 谓词决定。

一个写模型

Run / MemberTurn / dispatch / work graph 继续拥有执行、预算、暂停、恢复和终态。

一个读模型

消息、成员活动、handoff、轮次摘要都来自一个纯投影；UI 不再自己猜归属。

一个输入框

默认交给 Lead；@ 指定成员；“讨论”切换为依次发言。

一条时间线

Bot 回复是普通气泡；handoff 折成一行；trace 进详情抽屉。

三种形状，一套内核

single · Direct

一个 Bot，一个 MemberTurn。和 Group 用同一个 composer、同一个时间线组件。

fanout · Lead 主持

Lead 先答；需要分工时调用 group_send。子 turn 全部结算后，系统只唤醒一次。现有 work graph 不动。

roundtable · 讨论

选中的成员按顺序各说一次；后来者能看到前面人的公开消息；无话可说回 (pass)。圆桌禁止 group_send。

关键边界：圆桌不能递归派活。否则 Run 的完成条件会变成“模型是否停止递归”，work graph、wake、预算都要重新证明。 递归委派只属于 fanout；圆桌的完成条件保持为“所有预生成 turn 终态”。

为什么不是 Room / Round 表

A · Run-centric

Run 加 shape；圆桌预生成所有 turn；claim 顺序；pass。复用现有 work graph。选为骨架。

B · Room + Round

新增 rounds / round_decisions / RoundCoordinator。能表达跨 Run wave，但引入第二套协调状态，且没有解决圆桌/pass。

06 · tradeoffs

风险、验收、度量

风险与取舍

  • 延迟：sequential 比并行慢；只用于讨论/依次发言，派活仍默认并行。
  • 成本：N 个成员仍 N 次模型调用；sequential 不更便宜。lead-first 才是省钱手段。
  • Prompt 证据：依赖结果必须继续 exact join；不能靠同 Bot 后来的一条消息。
  • pass 与验证：pass 不能当成功证据；自动 Router 的 verification 不能被 discussion pass 绕过。
  • UI 复杂度：不为“轮次”新增 Run 卡片；用 per-member row + batch 分隔。
  • 兼容性：order 省略 = 现状；旧 daemon 不支持时拒绝，不静默丢弃。

验收清单

  • ✓ sequential：A→B→C 严格顺序；B/C prompt 精确含前序结果。
  • ✓ 取消 A 后 B/C 不启动；重启后从 durable 依赖继续。
  • ✓ 重复 requestId 不重复执行。
  • ✓ pass 不产生 public message；Run 正常完成；不进证据。
  • ✓ trace 刷新/重连/重启可回放；不泄漏私有 reasoning。
  • ✓ 旧客户端省略 order 行为 byte-for-byte 不变。

time-to-first-speaker

lead-first vs everyone；衡量群聊“响应感”。

为什么 xacpx 不应把正文 @ 变成路由

DS-Bot 和 Grok 都能从文本里解析 @，因为它们的目标是“聊天室”，消息本身就是控制面。xacpx 的目标是“可远程控制、可审计的多 Agent 执行”：

  • 文本可以来自模型、外部频道、提示注入；一旦它能触发副作用，就需要重新证明 sender、run、permission provenance。
  • xacpx 已经用 `group_send` 把 sender/run 绑定在运行时 capability 上；正文 @ 会绕过这层。
  • 人类输入的 @ 可以在客户端/适配器转成结构化 target；Bot 的 @ 只作为文本提及，不产生副作用。
为什么 xacpx 不应合并成员的群会话与私聊

Grok 的“统一历史”让成员在群里也记得私聊，体验自然；但 xacpx 的群会话按 Conversation×Topic×Bot 隔离，是证据/权限/恢复边界的一部分。

  • 合并后，群里的结果可能混入私聊内容，`group_read_result` 的公共性不再成立。
  • 不同 Group/Topic 的任务会互相污染，难以做 per-Topic 审计与 teardown。
  • 如果产品需要“记得用户”，应通过显式的 Bot memory / 私聊引用，而不是共享 Session。
为什么 DS-Bot 的 15 秒让出不适合直接照搬

DS-Bot 的回合可以“让出”是因为它把成员的最终回复和过程分开，群聊是唯一真相；xacpx 的 MemberTurn 是一次 durable claim，结果必须归到 exact sourceTurn/attempt。

  • 中途让出会让“谁的结果对应哪个 assignment”变得模糊，恢复时容易重复或丢结果。
  • xacpx 已有 trace，可以在不让出执行的情况下给用户“过程可见”。
  • 如果确实需要提前让出，应作为显式的“长任务后台化”设计，而不是群聊默认行为。
