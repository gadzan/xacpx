# xacpx 群组协作环境改造方案（产品版）

> 本文件是**产品版**：面向使用者，讲你在群组里看到什么、什么时候需要你、点一下能解决什么。
> 配套的**研发的技术方案版**（面向实现者，讲系统分层、数据、接口、护栏、验收测试）见同目录的《xacpx 群组协作环境改造方案（技术方案版）》。两版讲的是同一套改动，产品版定“用户看到什么”，技术版定“系统怎么实现”；两版冲突时，以本产品版为准。
>
> 状态：设计稿，待 Gadzan 审定。**未动任何代码、未动生产、未改 GOAL.md、未应用 2026-10-26 的纠正草稿、未解冻 P0。**
> 日期：2026-10-29。事实依据与技术版相同：生产群组 xacpx开发小组 2026-10-27、2026-10-28 的真实群聊记录。

## 0. 产品承诺，一句话

你提一个需求，就可以放下手机。活会自己往下走，并行去做，互相帮忙，审查自己出现；**做完了推你一次，卡住了推你一次，需要你决定推你一次，其他时候安静。**

现在的问题正好反过来：活要你一环一环推，审查要你开口才出现，卡住了要你发“hi”才有人理，主时间线还贴满了过程。你不是在用一个团队，你是在当调度员。本产品版就是要把调度员这个活从你手里拿走。

## 1. 谁在用，在哪用

- **主要使用者：群主，也就是你。** 你在手机（iOS 应用与 relay-web）上打开群组，提需求、看结论、做决定。你不是要学会一套调度系统，你是要一个能干活的团队。
- **次要使用者：群里的 bot。** 它们是干活的人，不是产品的界面。它们怎么发现彼此、怎么互相帮忙，是技术版的事；你只需要看到结果是对的、过程是可查的。
- **使用场景：** 通勤路上提一个需求，回来时已经有结论；开会间隙收到一条“卡住了，需要你选”的推送，点一下就继续；晚上打开群组，一眼就知道今天有没有需要你的事。

## 2. 产品原则

1. **一条主线。** 群组只有一个主界面：时间线加总览。不要再给用户第二个时间线、第二个任务板、第二个活动页。
2. **一个请求，一个答案。** 你提一个需求，最后只收到一个最终答案。中间过程默认折叠，点开能看，不点开不打扰。
3. **证据大于标签。** 不用“已完成”“达成”这种标签让用户相信，改动摘要加测试结果摆出来，十秒能验证。
4. **只在需要你时找你。** 正在忙、正在聊、正在并行跑，都不推你。推你的只有三件事：做完了、卡住了、需要你决定。
5. **一键能解决。** 每次找你，都附带可以直接点的选项，不是让你读完一篇总结再打字想办法。
6. **人话，不说系统词。** 界面上不出现跟进轮、唤醒轮、派发卡、裁决、批次、预算这些词（对照表见第 9 节）。
7. **随时能打断。** 你永远可以叫停、换人、换负责人、直接跟某个 bot 说话，而且是一键，不是走流程。

## 3. 界面结构：只有两个面，加一个详情

### 3.1 群组总览（打开群组第一眼）

放在群组顶部，一屏之内回答四个问题：

- 现在谁是负责人（名字加一句话说明，例如“负责人：幕僚长”）。
- 谁在忙、谁空闲、谁卡住了（每个成员一行：名字、状态、正在做的事一句话）。
- 现在有几件进行中的事，几件卡住了，几件需要你。
- 今天有没有需要你的事：如果没有，直接写“今天没有需要你的事”，不要让用户翻时间线去确认。

负责人换了，总览顶部出现一条提示：“负责人已换成架构师”，停留到用户看到为止，不要悄悄换人。

### 3.2 时间线（主界面）

时间线按你的请求组织，一个请求是一组，组内顺序是：

1. 你的请求（原文）。
2. 一行进行中状态（可折叠，例如“前端在做实现，架构师在看影响面”；状态变化时这行更新，不产生新消息）。
3. **一个最终答案**（见 3.3 节）。这是这组里唯一默认展开的结论。
4. 中间结论默认折叠（例如“前端的结论”“审查员的结论”），标题一行，点开能看全文，不点开不占地方。

不要出现的东西：70 行过程叙述、重复的基线检查、bot 的思考过程、派发卡的流水账。这些全部进详情。

### 3.3 最终答案长什么样

最终答案不是一张表，是三段人话，第一段必须能独立成立。示例（用真实的群组过滤任务改写）：

> **创建群组时，已禁用 bot 不会再出现在成员列表里。**
>
> 改了群组创建对话框的成员候选逻辑，创建模式只列已启用 bot，编辑模式保持原样。测试 28 项通过，类型检查通过。分支在 `feat/group-create-filter-disabled`，尚未提交。
>
> 还剩两件事：编辑模式下新增成员仍可选到已禁用 bot（按边界这次没动）；改动尚未提交和开 PR。
>
> [查看改动] [查看测试] [提交并开 PR] [再改一版]

格式要求：

- 第一行是结论，手机上一屏能看完，不用点开。
- 第二段是证据：改了什么、测试结果、分支状态。代码任务必须有改动摘要和测试结果，缺了就是没做完。
- 第三段是剩余项：已知局限、未验证项、下一步，一条都不能藏。
- 底部是操作按钮，不是让你打字：查看改动、查看测试、提交并开 PR、再改一版。合并 PR 永远需要你本人点，审查员说“可以合”不等于自动合（硬底线，技术版第 6 节）。

### 3.4 详情（点开才看）

任何一条结论、任何一个进行中的活，点开都能看到详情，详情里有：

- 完整过程（指令、步骤、原始记录），就是现在“查看执行过程”弹窗里的东西。
- 改动 diff 摘要，点开看完整 diff。
- 测试明细。
- 是谁找谁帮忙的（例如“前端找审查员帮忙看实现”），像真人 @ 那样可追溯。
- 卡住的原因和已经试过的方法（如果卡住了）。

详情是“查看原因”的入口，不是主界面。主界面永远保持干净。

### 3.5 审查长什么样

审查不是一张任务卡，而是一次可以直接操作的检查：

> **审查员 Bob 已看完前端的实现，结论：通过，有 1 条建议。**
>
> 改动：群组创建对话框成员候选逻辑；测试 28 项通过。
> 建议：编辑模式新增成员仍可选已禁用 bot，建议下次单独处理。
>
> [查看 diff] [通过] [要求修改]

审查人与实现人不是同一人，审查人与提交人不是同一人，这两条在界面上要能看出来（名字直接摆出来），而不是藏在系统校验里。审查通过后，提交和开 PR 是下一步操作，不是和审查绑在同一件事里——2026-10-27 把审查、提交、开 PR 派给同一个人，是本产品版要杜绝的用法。

## 4. 你需要出面的四种时刻

每次找你，都是一条消息加可以直接点的选项。没有选项的消息，不应该推给你。

### 4.1 做完了

> **群组过滤已完成，可以提交了。**
>
> 创建模式只列已启用 bot，测试 28 项通过，审查通过。
>
> [提交并开 PR] [再改一版] [先放着]

### 4.2 卡住了

> **审查员 Bob 中断了两次，需要你选一下。**
>
> 原因：连接中断，已试过重派一次，仍无结论。
>
> [换一个人审查] [让前端自己先改一版] [先放着，我晚点看]

卡住的消息必须写清：卡在哪、已经试过什么、你的选项是什么。只写“失败了”不算卡住通知。

### 4.3 有分歧

两个 bot 意见不一致时，不要让负责人悄悄替你选了，要把分歧本身摆出来：

> **架构师和前端对改动范围有分歧。**
>
> 架构师：只改创建模式，编辑模式不动。
> 前端：创建和编辑应该一起改，否则体验不一致。
>
> [按架构师的来] [按前端的来] [让他们再讨论一轮]

### 4.4 需要你决定

其他所有需要你拍板的事（例如是否合并 PR、是否改变任务范围、是否接受一个有已知局限的版本），都走同一个格式：结论一句话、选项摆出来、点一下就生效。

**如果用户不理会：** 卡住和需要决定的事，在总览里保持“需要你”的计数，不重复推送、不刷时间线；做完了的事，在总览里保持“待确认”，同样不重复推。安静地等你，而不是催你。

## 5. 你随时能做的操作

以下操作在任何进行中的活上都应该一键可达，不需要你先学会系统概念：

- **叫停：** 停止当前这条活的后续推进（已在跑的轮次按现有取消规则处理，取消后不再自动续派）。
- **换人：** 把卡住的活换给另一个同角色的 bot。
- **直接说话：** 直接跟某个 bot 说一句话，不用经过负责人转述。
- **换负责人：** 把负责人换成另一成员，换完顶部出现提示（见 3.1 节），座位行为保持一致。
- **查看原因：** 点开详情看过程、diff、测试，不用在时间线里翻。

 destructive 操作（例如删除群组、停止生产服务）不在本产品版的一键范围内，仍需单独确认，这是硬底线，不展开。

## 6. 通知规则

只推三类，其他一律不推：

| 推 | 不推 |
| --- | --- |
| 做完了（最终答案 ready） | 正在忙、正在并行跑、正在聊天 |
| 卡住了（见 4.2 节） | 某个 bot 开始了、某个 bot 发了中间结论 |
| 需要你决定（见 4.3、4.4 节） | 活动脉冲、状态变化、任务认领 |

通知文案就是最终答案或卡住消息的第一行，不要推“有新消息”这种空通知。点通知直接进到对应的最终答案或决定界面，不要只进到群组顶部让你自己找。

## 7. 用户旅程（按真实记录改写）

### 旅程 A：提需求，回来就有结论（正常情况）

1. 你在群里说：创建群组时自动过滤已禁用 bot。
2. 你放下手机。总览显示：前端在做实现，架构师在看影响面（并行，不用你排队）。
3. 前端做完，自己找审查员看实现（不用你问“为什么不审查”）。
4. 你收到一条推送：群组过滤已完成，可以提交了。点开是 3.3 节的最终答案，底部有“提交并开 PR”。
5. 全程你没有发过第二条追问消息。时间线里这个请求只有：你的请求、一行状态、一个最终答案，中间结论全部折叠。

### 旅程 B：卡住了，你点一下就继续

1. 审查员中断，无结论。
2. 系统自己续派一次，仍无结论。
3. 你收到一条卡住推送，写清原因和试过的方法，选项是换人、让前端先改、先放着。
4. 你点“换一个人审查”，活继续走，不需要你再打字解释。
5. 如果这时你正在忙，不点也行：总览里“需要你”计数加一，不重复推你。

### 旅程 C：你中途想改主意

1. 活正在并行跑，你发现方向要改。
2. 你点进这个活，点“直接说话”，跟负责人说一句话，或者点“叫停”停掉后续推进。
3. 已在跑的轮次按取消规则处理，时间线里出现一条简短说明：已按你的要求停止，下一步是什么。不出现过程刷屏。

### 旅程 D：两个 bot 有分歧

1. 架构师和前端对范围有分歧。
2. 你收到一条分歧消息，两边观点各一句话，选项摆出来。
3. 你点一个选项，活按你的选项继续；分歧本身留在详情里可查，不被负责人悄悄消化掉。

### 旅程 E：早上打开群组，什么都不用做

1. 你打开群组，总览写：今天没有需要你的事；进行中的事 2 件，卡住的 0 件。
2. 你不用翻时间线确认，直接放下手机。
3. 这是本产品版最重要的验收场景之一：没有需要你的事时，产品应该让你立刻知道，而不是让你翻完才放心。

## 8. V1 范围：先做三件，其他藏起来

V1 只做用户能立刻感受到的三件事，其他全部作为支撑藏在系统里，不单独做成用户功能：

**V1 做：**

1. 主时间线只发结论，而且一个请求只有一个最终答案（中间结论默认折叠，详情可查）。
2. 活会自己往下走：实现完成自动进审查，中断自动续派或换人，卡住了才找你；全程不需要你追问。
3. 并行是默认的：无依赖的活同时跑，有依赖的才等，不用你手动排队。

**V1 不单独做成用户功能（作为支撑实现，不给独立界面）：**

- 独立的任务板页面、独立的活动流页面（总览里的状态和筛选就是它们的全部用户形态）。
- 工作区隔离设置界面（按真实情况自动处理，只有真正共享目录时才需要用户感知）。
- 详细的 bot 统计、历史报表、复杂的任务状态机界面。
- 每 bot 记忆文件、plan 层确认门、硬阶段流水线（技术版第 9 节已明确不做）。

**V2 再考虑（V1 验证后再定）：** 总览里的任务筛选视图、活动历史查看、按 bot 的工作量总览、审查模板。这些都不在 V1 里承诺。

## 9. 界面语言对照表

界面上只出现右列，左列是系统内部词，不许出现在用户面前：

| 系统内部词 | 界面上的说法 |
| --- | --- |
| 跟进轮、唤醒轮 | 继续 |
| 派发卡 | 找某某帮忙 |
| 裁决 | 结果 |
| 任务主人 | 负责人（指某个任务的负责人，不是群组负责人时加任务名） |
| 批次 | 不出现（用户不需要知道批） |
| 预算、链深度 | 不出现（内部安全网，见技术版） |
| indeterminate、未证 | 卡住了，原因写清（例如“结果无法确认”） |
| completed（轮次结束） | 不单独展示；只展示结果是完成、未完成还是无结论 |

## 10. 产品验收标准（用产品的方式测，不用代码的方式测）

以下每条都应该能通过实际使用验证，而不是只看测试通过：

1. 打开群组，十秒内能回答：今天有没有需要我的事、谁卡住了、谁在忙。
2. 提一个正常需求，全程不发第二条追问消息，就能收到最终答案（对应 2026-10-27、28 两次追问的反例）。
3. 一个请求的完整时间线，默认展开的只有：你的请求、一行状态、一个最终答案；其他全部折叠。
4. 最终答案第一行能独立成立，手机上一屏看完；改动摘要和测试结果在答案里，不用点进详情才知道。
5. 卡住时收到的消息写清原因、试过的方法和可点的选项；不点时不重复推送，总览计数正确。
6. 审查请求点开就是 diff 和结论，点“通过”或“要求修改”即生效，不用再派一次任务。
7. 负责人换了，总览顶部有明确提示；换完之后行为一致，不用人重新教。
8. 两个 bot 有分歧时，分歧本身出现在你面前，而不是被负责人悄悄选掉。
9. 没有需要你的事时，总览直接写出来，不用你翻完时间线才放心。
10. 任何进行中的活，你都能一键叫停、换人、直接说话、换负责人。

## 11. 产品成功指标（提议值，实施后复核）

- 每个正常任务的用户追问消息数：目标 0（现在是 2 次，见 2026-10-28 的审查与续派）。
- 每个请求默认展开的消息数：目标不超过 3 条（请求、状态、最终答案）。
- 从提需求到最终答案，中间不需要用户介入的任务占比：目标先定 80%，跑一个月后再复核。
- 卡住后用户一次点击就能继续的比例：目标 90% 以上（其余是确实需要打字说明的新情况）。
- 通知打开后直达最终答案或决定界面的比例：目标 100%，不允许点通知后还要自己找。

以上是产品目标，不是技术承诺；技术版的预算、深度、并发上限是实现这些目标的安全网，不是用户指标。

## 12. 产品待定问题

1. 通知通道：relay-web 与 iOS 应用的推送以哪个为准？做完了、卡住了、需要决定三类，是否都走同一通道？
2. 合并 PR 的按钮放在最终答案底部，还是单独的 PR 界面？本产品版提议放最终答案底部，待你确认。
3. 换负责人、叫停、换人这些操作，是否只有群主能点，还是群里任何人都能点？本产品版提议只有群主能点关键操作，待你确认。
4. 分歧消息的选项：除了两边观点外，是否永远保留“让他们再讨论一轮”？本产品版提议保留。
5. 总览里的“今天没有需要你的事”，是以自然日算，还是以“自你上次查看以来”算？本产品版提议以后者为准，待你确认。
