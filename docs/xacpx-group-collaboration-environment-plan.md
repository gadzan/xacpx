## 0. 一句话目标

让群组里的 bot 像真人团队一样工作和协作：**能发现彼此、能直接搭话、能互相委派、能并发运行**。

实现手段是**给环境，而不是加硬流程**。负责人是一个系统座位，不是某个 bot 的人设；协作能力来自可见性、可达性、可加入性，而不是一串审批门。流程只在必须成立的地方进代码，其余全部降级为环境和轻规范。

本方案取代 2026-10-28 白天先提出的“硬门流水线”方向。那套方向的问题是：把审查门、裁决、阶段推进都做成硬约束，协作本身反而更难。用户随后连续纠正的方向，才是本方案的基准：

1. 负责人要系统化，不是复制到幕僚长指令里的一段规则。
2. bot 要像真人一样协作，不要太多系统性限制，关键是发现与主动协作的环境。
3. 唤醒轮不能委派新任务的限制要放开，否则 bot 很难协作，放开时用护栏兜底。
4. bot 之间要能互相委派、沟通、通讯，并且并发运行，而不是现有的串行。
5. 群组不是公共工作区，不应因同在一个群组就默认串行；并行应放开，只有真正证明是同一物理目录的写操作才需要排队。
6. 群聊主时间线只发每个 bot 在 stop 时的最终结论，过程文本不贴主时间线，过程细节只留在执行过程详情里。

## 1. 问题诊断：来自真实群组记录的证据

### 1.1 串行是流程造成的，不是引擎跑不动并行

- 2026-10-27：15:49 负责人派架构师 → 16:04 取消 → 16:05 重派架构师 → 16:49 完成 → 17:11 派 Bob；2026-10-28：16:39 派前端 → 17:54 完成 → 17:58 负责人自查 → 18:06 派 Bob。每一步都等上一步结束。
- 引擎里其实已有并行模式、依赖关系（`dependsOn`）、按批结算、全局并发上限（默认 8）、话题并发上限（1–64）。生产群组的串行，来自负责人一轮只派一个、派完等唤醒、唤醒不能再派、每一步还要等用户发新消息。

### 1.2 用户在当调度员

- 审查门两次都不是自动出现的：围栏修复完成于 2026-10-27 16:49，负责人自查于 16:53，未派审查；直到用户 17:08 说“提交并开 PR”，才把审查、提交、开 PR 一起派给 Bob。群组过滤完成于 2026-10-28 17:54，负责人自查于 17:58，未派审查；直到用户 18:05 问“为什么不让审查员审查”，负责人才承认遗漏并派 Bob。
- Bob 2026-10-28 18:08 中断后，负责人和 Bob 都没有自行续派；直到用户 18:10 问“为什么不重新唤醒他继续”，才重派。18:12 第二次仍无结论，18:15 第三次续派被运行时以“唤醒回合不能派发新任务”拒绝，之后到 18:56 用户发“hi”之前，群里没有任何跟进。

### 1.3 互相协作被主动压住

- 成员之间互相委派，整个两天记录里只有 1 例：2026-10-27 架构师把只读溯源转派给前端开发。
- 2026-10-28 负责人派前端时明确写“无需再次转派”，前端也引用这句话原地执行。协作不是没能力，而是被负责人明令禁止了。
- 跨会话消息的现有提示也是反协作的：只允许“关键信息”或“必须由对方决定的事”，不许闲聊、不许确认、不许问进度。真人团队不可能按这个工作。

### 1.4 “已完成”不等于目标达成

派发卡上的“已完成”只表示成员轮次结束了，不表示目标达成了。两天里有 4 例卡片已完成但目标未达成：架构师第一轮（负责人判定无证据，取消重派）、Bob 的审查加提交加开 PR（从未提交、从未开 PR）、Bob 的独立审查（中断，无结论）、Bob 的继续审查（只有进度，无结论）。结论只能从消息正文里读，卡片状态本身不可信。

### 1.5 角色混同与事前检查缺失

- Bob 一次被同时派了审查、提交、开 PR 三件事，审查的独立性当场丢失；负责人接手后自己也直接执行了工作。
- 已有 PR #483（修复 stale admitted fence 阻塞删除，`2973e56a`，Open 未合并）是在 Bob 提交失败、负责人接手查询后才发现的，事前没有任何“已有 PR / 已有分支”检查。
- 三个未提交工作树散落：`D:\project\bob-xacpx`、`D:\project\bob-xacpx-fix-session-release`、`D:\project\xacpx-groupfilter`，群里没有统一的分支与 PR 台账。前端的 4 项已知局限、线上删除未复验、过滤改动未部署，都没有变成后续任务。

### 1.6 过程文本刷屏主时间线

每个成员轮次在主时间线只占一条消息，但那条消息就是全过程叙述，结论只是有时附在最后，有时根本没有：

- 前端群组过滤轮次（2026-10-28 16:39 派发，17:54 发消息，耗时 74:58）：约 70 行过程叙述在前，7 节实施报告在后，过程是消息主体。
- 架构师围栏修复轮次（2026-10-27 16:49）：100 多行过程文本在前，6 节报告在后，过程占绝大多数。
- Bob 继续审查轮次（2026-10-28 18:14）：约 8 行，**只有过程、没有结论**，其中同一条基线检查行重复了 4 次。这是最有力的证据：没有结论时，主时间线照样贴过程。
- “查看执行过程”弹窗是另一份记录：状态、话题、耗时、折叠的派发指令、思考按钮、分页的原始事件流。它已经保存了过程细节，主时间线再贴一遍过程是纯重复，删掉不丢失信息。

### 1.7 群组工作区被误当成公共工作区

- 群组成员的执行工作区名来自话题的执行目标（`snapshotGroupMemberProfile`：话题目标 wins，bot 默认工作区不泄漏），但话题工作区名是逻辑名，话题的 cwd 在现有代码里只是元数据、启动时并不真正生效。拿逻辑工作区名当物理重叠来串行，是判错了对象。
- 生产实证：架构师在 `bob-xacpx`，前端在 `xacpx-groupfilter`，本来就是两个不同目录，却还是被串行派发排成了单线。
- 代码的跨轮次准入规则本身已经是物理目录标准：不同物理目录永远不冲突；只有同一个规范化后的目录，才只允许已证明的只读轮次重叠，其他写操作拿写者槽位，冲突时排队等而不是失败。串行的触发条件应该是“证明是同一个目录且都要写”，而不是“同在一个群组”。

## 2. 设计原则

1. **环境大于门。** 先给发现、在场、直达、认领、并行这些环境能力，再谈约束。约束只留给安全与正确性，不留给协作流程本身。
2. **并行默认，依赖才串行。** 没有依赖关系的任务同批并行；有依赖的，等依赖完成再启动；同一物理目录的两个写操作，才排队。
3. **聊天与委派分开。** 非正式沟通不产生任务、不结束轮次、不需要唤醒；正式委派产生任务、有归属、有结果回流。把聊天硬塞进任务系统，是串行的根源之一。
4. **负责人是座位，不是人。** 无论哪个 bot 被分配成负责人，座位行为一致：座位层由系统注入，优先于 bot 个人指令；换负责人时，座位层与状态自动跟过去，不用人工复制。
5. **呈现与执行分离。** 主时间线只发最终结论；过程、思考、原始事件只留在执行过程详情里；活动与状态走另一条轻量通道，不刷主时间线。
6. **只在证明处串行。** 串行、排队、隔离，都必须以可证明的事实为依据（同一规范化物理目录、同一文件、已证明的只读与否），不能以“同群组”“同话题”“效果未知”这种未证明的理由一律串行。
7. **硬底线最小集，只放代码。** 不冒充他人、不动生产、不合并需要 Gadzan 确认的 PR、不派给已禁用或被隔离成员、用户取消与未证结果封停不变。其余全部是环境与轻规范。

## 3. 目标环境长什么样

以群组过滤那条线为例，改造后应该这样走，全程不需要用户追问：

1. 用户提需求：创建群组时自动过滤已禁用 bot。
2. 负责人同时派两件事（同一批，并行）：前端做过滤实现，架构师并行看目录与成员数据的影响面。两人各有自己的工作面，不互相等。
3. 前端做完，不用等负责人，也不等用户问，直接找 Bob：“帮我看一眼实现，重点是创建模式与编辑模式的边界。”这是非正式搭话加正式审查委派的组合：搭话不产生任务，审查委派产生一个有归属的任务，Bob 并发执行，前端继续处理自己的收尾。
4. 架构师在活动流里看到前端的进展，顺手补一句目录影响，不用经过负责人转述。
5. Bob 若中断，派发方（前端）的跟进轮总结中断原因后直接续派或换人，不需要用户在 18:05、18:10 两次追问。跟进轮本身也可以继续派发（见第 4.4 节的护栏）。
6. 审查通过后，任务主人（前端）汇总最终结论，负责人只做最后的群组级汇总：改了什么、测试证据、剩余局限、下一步。主时间线只出现这两条结论，不出现 70 行过程。
7. 已有 PR 检查在派发前自动完成：如果已有 PR #483 这类现成修复，系统先告诉派发方，不再重复派提交任务。

负责人全程的角色是：开局分活、没人接的活有人接、卡住的活有人帮、最后汇总。负责人不再是每一步的必经之路。

## 4. 分层改动方案

### 4.1 负责人座位层：系统注入，换人不变

**现状缺口。** 提示组合（`composeBotTurnPrompt`）是“你是名为 X 的 Bot”加个人指令，再加一句“Bot 档案不改变模型、工具与权限策略”。没有任何负责人专属提示层：一个 bot 当上负责人，除了工具上下文外，提示与当成员时没有区别。行为今天完全依赖负责人 bot 的个人指令。

**改动。**

- 在提示组合时注入一层**负责人座位提示**，触发条件是：本轮次的 botId 等于群组的 `leadBotId`，且本轮次是负责人轮次。注入位置在 bot 个人指令**之前**，并明文写清优先级：座位层优先，个人指令是背景；冲突时座位层胜出。
- 座位提示必须是**版本化的代码产物**，不是某个 bot 档案里的一段手写文字；每次运行可复现、可回放、可随快照版本比对。群组换 `leadBotId` 时，新负责人自动获得同一层座位提示与同一份状态快照，不用人复制、不用改档案。
- 座位提示只写座位行为，不写具体业务规则：发现成员、并行分活、牵线、处理无人接与卡住的活、汇总结论、把未完成项变成后续任务。它不应该是“调度规则全文”，规则全文是本方案，不是提示词。
- 负责人 bot 当成员干活时，座位层不注入；它的专业能力（架构、前端、审查）只在成员轮次里生效。座位与专业，两层分开。

**明确不做。** 不在 relay-web 界面里只改幕僚长 bot 的个人指令。那样做是把行为绑在一个 bot 身上，换负责人、提示被截断、唤醒轮受限时全部失效，且修不了唤醒、状态语义、呈现、重复 PR 这些系统问题。

### 4.2 发现与在场层：让 bot 能看见彼此

**现状缺口。** 每次群组执行前置的成员上下文只有：成员列表（botId、名字至多 200 字、是否启用、是否被隔离而不可运行）加一段协议文本。没有谁在干嘛、卡在哪、刚做完什么、擅长什么、工作区与分支状态。bot 根本发现不了彼此。

**改动：负责人与成员轮次都注入一份系统生成的结构化快照，不是静态文本。**

快照字段（系统实时生成，bot 不用凭记忆写）：

- 花名册：botId、名字、角色、是否启用、能力标签、工具与环境健康状态、当前负载。
- 在场状态：空闲、进行中、卡住、已完成，及其对应的任务与卡点（见 4.2 活动流）。
- 流水线与任务板状态：进行中的任务、已认领的任务、无人接的任务、被阻塞的任务、已结算任务的裁决（不是原始文本）。
- 工作面地图：各成员当前工作树、分支、已有 PR（例如 PR #483 这类现成修复必须在派发前可见）、未提交工作树清单。
- 预算与唤醒信息：本轮次剩余轮次预算、唤醒链深度（见 4.4 节）、唤醒类型。
- 依赖图：哪些任务无依赖可并行、哪些任务依赖哪条已结算结果。

**活动流（与主时间线分开）。** 主时间线只发最终结论（见 4.7 节），但另外需要一条轻量活动通道，让其他 bot 能发现谁需要帮忙：

- 每条活动是三行脉冲：现在在干嘛、卡点、下一刀。不是过程全文，不是刷屏。
- 活动流不进入主时间线，不计入最终结论，不作为任务裁决的依据；它只用于发现与牵线。
- 活动由系统根据轮次状态生成，bot 也可以主动发一条状态脉冲；系统生成的优先于 bot 自报的。

**任务板。** 所有人可见的共享任务板，状态由系统维护：

- 状态：待认领、已认领、进行中、被阻塞、已结算（附裁决）、已放弃。
- 认领是一个声明，不是一次审批；认领后任务板即时可见，防止重复做。
- 无人接与被阻塞的任务，负责人座位层有责任牵线，而不是等用户发现。

### 4.3 通讯层：聊天与委派是两条通道

这是本方案最关键的一次拆分。现状把所有成员间通讯都压进“派发任务”这一条通道，才会处处串行。

|  | 非正式 peer 聊天 | 正式互相委派 |
| --- | --- | --- |
| 目的 | 问一句、提醒一句、讨论一句、同步进展 | 把一个子任务交给对方做，期待结果回流 |
| 是否产生任务 | 否 | 是，产生一个有归属的成员轮次 |
| 发送方是否停下 | 否，双方继续手里的活 | 否，发送方继续自己的活（见 4.4 节），结果回流时再跟进 |
| 是否需要负责人批准 | 否 | 否，任何成员都可派（见 4.4 节） |
| 是否需要唤醒轮 | 否 | 结果回流走跟进轮（见 4.4 节），不是靠用户发新消息 |
| 是否计入最终结论 | 否，只进活动与私聊记录 | 是，结算后产生裁决与最终结论 |
| 呈现 | 活动流与对话记录，不上主时间线 | 派发卡（标明派发人）加最终结论上主时间线 |

**改动。**

- 群组内新增（或从现有消息腿分出）一条**非正式 peer 聊天通道**：任何成员可直接找任何启用成员，带 `replyTo` 链；聊天不创建成员轮次、不消耗任务预算、不要求结束本轮、不触发唤醒。聊天记录可查，但不上主时间线。
- 现有跨会话消息提示必须翻转：删掉“只允许关键信息、不许闲聊、不许确认、不许问进度”的限制，改为“高价值沟通优先，但询问、提醒、同步、讨论都是合法用途；不要无意义刷屏”。刷屏由预算与活动流节流控制，不由禁令控制。
- 正式委派复用群组派发通道（`group_send` 语义），但去掉“派发方必须是负责人”的习惯性限制，见 4.4 节。
- 派发卡必须标明**派发人**。现状派发卡不标派发人，身份只能从负责人日志文本里推断；改为元数据里的派发人字段，卡片与详情都展示，像真人 @ 那样可追溯。

### 4.4 委派与跟进层：派发不结束发送方，唤醒轮可以继续派

**现状缺口（两条）。**

- 派发提示写的是：派完所有任务后立刻结束本轮，不要等待、不要轮询；结算后系统只在跟进轮里唤醒你一次。派发方派完就退场，无法边干边协作。
- 跟进轮（唤醒轮）被代码明确禁止派发新任务（`handoff_from_followup_refused`），理由是防止唤醒、派发、唤醒无限连锁烧掉轮次预算。跟进轮的任务也被写死为“读结果、总结给用户”。

**改动：把跟进轮从“只能总结”改成“总结加可继续”，并把跟进能力推广到所有派发方，不只是负责人。**

1. **任何成员都可以是派发方。** 派发校验保持现有硬条件不变：发送方与目标方必须是当前成员、目标方已启用、目标方不是发送方本人、话题有效、执行绑定仍匹配。在此之外，不再要求发送方是负责人。
2. **派发不结束发送方。** 发送方派发后，自己的轮次可以继续自己的工作；派发任务在后台并发执行。发送方不再被要求“派完立刻结束”。如果发送方确实无事可做，它可以主动结束并等待跟进轮，但这应该是选择，不是强制。
3. **任何派发方都获得跟进轮。** 派发方派出的任务全部结算后，系统给派发方插一个跟进轮（与现有负责人唤醒轮同机制）。跟进轮的任务是：先读已结算结果、写出裁决，再决定是汇总、续派、换人还是升级给用户。
4. **跟进轮可以派发新任务，但有界。** 这是用户明确要求的放开，护栏如下（数值是本方案的提议值，见第 10 节待拍板）：
   - **链深度上限：3 轮（可配置）。** 跟进轮派发的新任务结算后产生新跟进轮，链深度加 1；到顶后停止自动继续，汇总现状并升级给用户，而不是继续循环。
   - **预算预留。** 派发前检查剩余轮次预算，至少留一个跟进轮的名额；预算耗尽时明确报预算耗尽，而不是像现在这样静默不插跟进轮。
   - **先读后派。** 跟进轮必须先用结果读取工具读完已结算结果、写出裁决，才能派发；不能只看任务清单就派。
   - **防重复派发。** 同一任务内容、同一目标、同一轮不得重复派；重试必须带失败原因与不同的方法，防止空转。
   - **跟进轮按批次算，不按派发方一生算。** 现有“一个派发方只能有一个跟进轮”的唯一性 guard 必须改为“一个派发方在每一批任务里可有一个跟进轮”，否则第二轮、第三轮没有人总结、没有人继续。
   - **取消与未证封停不变。** 用户取消的派发方不产生跟进轮；任一任务为未证（indeterminate）时，不产生跟进轮且 Run 按现有规则封停；被隔离成员不可派。
   - **可见与可叫停。** 跟进总结与下一轮派发在时间线与详情里分开显示，并标明链深度；用户随时可取消整条链。
5. **结果回流方式。** 正式委派的结果回流复用跨会话消息已有的完成模式语义：无回执、仅通知、回传有界最终结果，三档由派发方在派发时声明；回流的是有界最终结果，不是过程全文。跟进轮读结果时，同样只读有界最终结果与裁决字段。

**明确不做。** 不直接删掉跟进轮禁派检查了事。删检查会放出无限连锁、预算烧光、基于未证结论派发、跟进轮唯一性断链这四个问题，护栏就是用来兜这四件事的。

### 4.5 并行与调度层：并行默认，依赖才串行

**现状缺口。** 默认路由的规则是“一轮一派”：已有已结算任务就直接结束，不再派新任务；这条规则适用于自动模式，不应被负责人模式继承。负责人模式的实际串行，来自负责人一轮只派一个加跟进轮不能再派，不是路由引擎本身没有并行能力。

**改动。**

- 负责人与任何派发方在一轮里可以派多个任务；无依赖的任务进入同一批并行执行，有依赖的任务挂 `dependsOn`，等依赖的已结算结果到达后再启动。
- 批内成员共享同一份参考集（冻结记录加被引用的行），并行成员不互相污染；顺序成员只追加已完成的依赖结果。这是现有冻结记录语义，保持不变。
- 批结算不等于全组停工：一个成员提前完成且其依赖已满足时，可以启动下一阶段工作，不必等整批全部结算。调度依据是依赖图，不是批次。
- 并发上限只做安全网，不做流程：全局默认同时跑 8 个执行、话题上限最高 64、自动轮次预算 24，这些是防主机被拖垮的上限，超了排队等，不应因此把协作改成串行。群组话题的并发上限应按群组规模显式配置（例如 4 人群组设为 4–8），而不是留空后被保守默认值串行化。
- 负责人座位提示要写明：独立任务并行派，不要凭感觉排成单线；只有依赖关系与同一物理目录写冲突（见 4.6 节）才是串行的理由。

### 4.6 工作区与资源准入层：群组不是公共工作区

**原则。** 群组不是公共工作区，不应因同在一个群组就默认串行。并行是群组默认值，串行只留给“证明是同一物理目录的两个写操作”这一种情况。

**改动。**

- **串行判定收窄到物理事实。** 只有当系统证明两个写轮次指向同一个规范化后的物理目录（规范化规则与现有资源准入层一致：真实路径、Windows 路径折叠、8.3 短名解析，同一规则、不许两套规则），且双方都不是已证明只读时，后一个才排队等前一个结算。逻辑工作区名、话题 id、bot 名，都不能作为串行依据。
- **群组话题的隔离默认值要修正。** 现有代码在目标缺失时默认读成保守的单写者（`shared-single-writer`），这是为共享目录准备的 fail-closed，不应套在不是公共工作区的群组上。建话题时按真实情况选隔离策略：各自独立工作面就选各自目录或每人独立工作区；只有真正共享一个目录时，才选单写者。已存话题的默认值迁移方式见第 10 节待拍板（只改新建话题，还是连同已存话题一起迁移）。
- **只读与非文件任务不进写者槽位。** 已证明只读（声明加强制执行证明，两者齐全）的轮次，即使同目录也能重叠；纯讨论、纯沟通、纯审查结论的轮次，不应参与文件准入。效果未证明就一律按写者处理的做法，必须改为按声明效果加证明分级：已证明只读可重叠、未证明写操作按写者排队、未声明效果的轮次在派发时就要求补声明，而不是事后一律串行。
- **真正共享一个目录才是需要隔离的特例。** 那时才启用每人独立工作区：每人一个已验证的工作区，启动时验证引用，结束时整合；整合由任务主人负责，冲突时由任务主人或负责人出面协调，不是由事前串行来避免。工作区隔离是特例的解法，不是所有群组并行的前置条件。
- **跨轮次准入保持现有语义。** 不同物理目录永远不冲突；同一目录的冲突是排队等（保持认领、租约、来源不变，待冲突释放后重跑），不是失败、不是把用户请求终结。这一点现状已经做对，保持不变。

### 4.7 呈现层：主时间线只发最终结论

**用户已定规则（本方案直接落地，不再讨论）。** 群聊主时间线只发每个 bot 在 stop 时的最终结论；过程文本不贴主时间线；过程细节只留在执行过程详情里。

**改动。**

- 成员原始输出进入执行过程详情（即现有的“查看执行过程”弹窗所对应的记录：指令、思考、原始事件流、分页加载），不再原样成为公开结果消息。
- 系统从成员输出中提取或要求成员输出一份**结构化最终报告**，再把这份报告发到主时间线。报告字段（提议，见第 10 节待拍板）：
  - 裁决：达成、未达成、中断，附原因。
  - 改动：改了哪些文件、哪个分支、哪个 PR（若有）。
  - 测试证据：跑了哪些测试、结果、已知基线失败是否已排除。
  - 剩余项：已知局限、未验证项、下一步。
  - 尝试过的阻塞：失败时尝试过的方法与证据，不是只有“失败了”。
- 报告缺失或格式不合规时，系统不贴过程文本兜底，只发一条简短的 stop 通知：原因、无结论、下一步。缺结论的轮次（如 Bob 2026-10-28 18:14 那轮）就应该只表现为这样一条通知，而不是 8 行过程。
- 派发卡与结果卡的状态语义必须分开：轮次结束（completed / failed / cancelled / indeterminate）是轮次状态，目标达成是裁决字段。卡片上不得再用“已完成”暗示目标达成；裁决缺失时，卡片应明确标“无结论”。
- 派发卡标明派发人、目标人、依赖关系、链深度；跟进总结与下一轮派发分开显示。

### 4.8 失败与收尾层：失败是流水线状态，不是等人来问

**改动：把失败处理做成跟进轮里的标准转移，而不是等用户干预。**

- 失败转移顺序（跟进轮里按序尝试，每步有预算上限）：按检查点与成员轮次记录恢复 → 换方法或换通道重试 → 换给同能力成员 → 升级给用户并附选项。
- 卡住检测在系统层做：轮次超时、派发方跟进轮长期无动作、任务板上有长期无人接或被阻塞的任务，都要在活动流与负责人快照里可见，而不是等用户发“hi”才发现。
- 每个任务始终有一个主人：主人负责最后结论；其他人是帮手；没人收尾时，负责人出面收尾。主人不是审批人，主人是收尾责任人。
- 剩余项不丢失：前端的已知局限、线上删除未复验、过滤改动未部署、围栏修复未提交这类剩余项，必须在最终报告里列出，并自动变成任务板上的后续任务，而不是散落在消息正文里。
- 审查独立性只保留最小硬约束：审查人与实现人不是同一人、审查人与提交人不是同一人，这两条进代码校验；其余审查流程（何时审查、审查后谁改、改完谁复查）走跟进轮的正常协作，不做成硬流水线。

## 6. 不变的硬底线

以下内容本方案不改动，实施时不得以“放开协作”为由顺带放开：

- 合 PR 只能由 Gadzan 本人授权；审查员说“可以合”只是建议，不是可执行指令。
- 生产机上禁止构建；停、删生产库或数据卷、主机重启、不可逆基建变更，必须 Gadzan 确认。
- 密钥不进聊天、不进记忆明文、不进备份仓库。
- 不派给已禁用成员、不派给被隔离成员、不派给非当前成员、不派给自己。
- 用户取消的派发方不产生跟进轮；任一任务为未证（indeterminate）时，Run 按现有规则封停，不产生跟进轮。
- 成员结果是不可信的成员数据：跟进轮只读有界最终结果与裁决字段，不把成员原始输出当任务文本直接派发。
- 现有 orchestration 链的 per-task 审批语义不动；本方案只改群组系统，不改 orchestration 链。

## 7. 实施顺序

每一步都可独立测试、独立回滚；前一步未通过验收，不进入下一步。

1. **负责人座位层加状态快照（不改行为）。** 只加座位提示层与快照字段，派发、跟进、呈现逻辑原样不动。验收：换负责人时座位行为一致；快照字段齐全且可复现。
2. **呈现层：主时间线只发最终结论。** 原始输出进详情，最终报告上时间线，无报告时只发 stop 通知，轮次状态与裁决分开显示。验收：第 8 节场景 E 通过。
3. **通讯层拆分：聊天与委派分开。** 群组聊天通道上线，翻转闲聊禁令，派发卡标明派发人。验收：聊天不产生任务、不结束轮次；派发卡可追溯派发人。
4. **跟进轮放开加护栏。** 跟进轮可派发，链深度、预算预留、先读后派、防重复、按批次计唯一性、取消与未证不变，全部落地。验收：第 8 节场景 A、B、C 通过。
5. **并行与任务板。** 并行默认加依赖图、任务板与活动流上线、负责人不再是唯一派发人。验收：第 8 节场景 D、F 通过。
6. **工作区准入收窄。** 串行判定收窄到同一物理目录写操作，只读与非文件任务不进写者槽位，话题隔离默认值修正，真正共享目录时才启用每人独立工作区。验收：第 8 节场景 G、H 通过。

## 8. 验收测试：基于真实群组历史的场景

以下场景全部取自或改编自 xacpx开发小组的真实记录，实施时应写成回归测试或演示脚本，不只靠人工看。

- **A. 实现完成自动进入审查。** 前端实现完成并结算后，派发方跟进轮直接派 Bob 做独立审查，审查人与实现人不同、与提交人不同；全程不需要用户发消息。对应真实缺口：2026-10-27 16:49 与 2026-10-28 17:54 两次审查门缺失。
- **B. 审查中断后自动续派。** Bob 审查中断（无结论）后，派发方跟进轮总结中断原因后直接续派或换人，不需要用户追问；卡片状态不得标为“已完成即目标达成”，应标“无结论”。对应真实缺口：2026-10-28 18:08、18:12、18:15 三次续派失败。
- **C. 跟进轮链深度与预算。** 跟进轮连续派发三轮后到顶，停止自动继续并汇总升级给用户；预算耗尽时明确报预算耗尽，不静默丢跟进轮；基于未证结果的派发被拒绝；同一任务重复派发被拒绝。
- **D. 并行分活。** 同一批里两个无依赖任务并行执行，互不等待；有依赖的任务等依赖结算后再启动；负责人一轮可派多个任务。对应真实缺口：两天全程串行。
- **E. 主时间线只发结论。** 一个输出 100 行过程文本的成员轮次，主时间线只出现结构化最终报告；一个无结论的轮次，主时间线只出现一条简短 stop 通知（原因、无结论、下一步），不出现过程文本。过程全文仍可在执行过程详情里查到。
- **F. 成员互相委派。** 非负责人成员可直接派给另一启用成员，派发卡标明派发人，派发方继续自己的工作，结果回流时派发方获得跟进轮；聊天不产生任务。对应真实缺口：两天仅 1 例成员转派且随后被禁。
- **G. 非公共工作区并行。** 两个成员在不同物理目录工作时并行执行，不被串行；两个成员在同一物理目录且都写时，后一个排队等，不失败；已证明只读的轮次即使同目录也可重叠；纯讨论轮次不进写者槽位。
- **H. 已有 PR 不重复派。** 派发提交任务前，系统先查已有 PR 与分支台账；已有 PR #483 这类现成修复时，告诉派发方而不重复派提交任务；未提交工作树清单在快照里可见。
- **I. 换负责人行为一致。** 把群组 `leadBotId` 换成另一成员后，座位行为、快照、跟进、汇总一致，不用人复制指令。
- **J. 取消与隔离不变。** 用户取消后不产生跟进轮；未证任务封停 Run；已禁用与被隔离成员不可派；以上任一被破坏即判定为回归。

## 9. 风险与取舍

- **聊天循环与预算烧光。** 放开聊天与跟进链后，bot 可能互相喊话、反复派发。兜底是链深度上限、轮次预算、预算预留、防重复派发、活动流节流，不是再加一道审批门。
- **并行冲突。** 同一文件被两个人同时改，可能在整合时冲突。取舍是：事前不串行，事后整合；整合责任归任务主人，冲突时由任务主人或负责人协调。事前串行看似安全，实际是把协作本身关掉了。
- **重复做。** 并行加认领声明后，仍可能出现重复。兜底是任务板可见与认领即时可见，重复时合并结果，不算失败。
- **基于未证结论派发。** 跟进轮放开后，最大的正确性风险是拿着没证实的结果派下一轮。兜底是先读后派、未证不产生跟进轮、成员结果只读有界最终结果与裁决字段。
- **活动流变第二条刷屏通道。** 活动流如果放开全文，就会重蹈主时间线的覆辙。兜底是三行脉冲、系统生成优先、节流、上主时间线的仍只有最终结论。
- **座位层优先于个人指令的争议。** 座位层胜出是座位一致性的前提，否则换负责人就换行为。但这也意味着 bot 的个人风格在负责人轮次里要让位于座位行为，这是本方案有意为之的取舍，不是 bug。
- **本方案刻意不做的事。** 不做硬阶段流水线（立项、实现、测试、审查、提交、验证的强制顺序门）；不做 plan 层确认门（代码里没有 plan 概念，见 2026-10-26 审计）；不做每 bot 记忆文件（代码里没有，记忆回流是另一个议题）；不把负责人座位层写成幕僚长个人指令。
